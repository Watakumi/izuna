## 一行で

**自分のコードを自分のインフラに置いたまま、複数の Claude Code を並列に走らせる開発環境。**

---

## なぜ作るか

Claude Code の GUI は既に飽和している。それでも作る理由は一点だけで、
**self-hosted forge を前提にしたものが無い**からである。

調査で確かめた事実（2026-09-07）:

| 既存 | 並列エージェント | self-hosted forge |
| --- | --- | --- |
| Claude Code 公式デスクトップ | worktree で対応 | GitHub 前提 |
| Nimbalyst（MIT / 1.7k★ / 5,936 commits） | worktree で対応 | **無い** |
| Conductor | 対応 | 不明（クローズド） |
| Clarc | 無い | 無い |

Nimbalyst のソースを実際に読んで数えた結果:

- `forgejo` を含むファイル: **0**
- `gitea` を含むファイル: **0**
- GitHub 連携は `gh` コマンドの shell 起動が 22 ファイル。API クライアントは無い
- `forgeUrl` / `baseUrl` / `selfHosted` に相当する設定項目が**存在しない**

つまり既存のどれも、**自分の forge を向けられない**。`gh` は GitHub Enterprise までで
Forgejo には向かない。ここが空いている。

## 誰のための道具か

作者ひとり。**コードを他人のサーバに置きたくない**が、
エージェントによる並列開発の効率は欲しい人。

汎用製品として競合に勝つことは目標にしない。機能の多さで Nimbalyst に
追いつく必要も無い。**自分の運用に噛み合うこと**だけが評価軸である。

## 三本の柱

### 1. 並列エージェント（ブレインと実行役）

一つのリポジトリに対し、複数の Claude Code セッションを
**それぞれ独立した git worktree** で同時に走らせる。
さらに、**ブレイン（指示役）が実行役を統率する**。

- セッションごとに worktree とブランチが自動で生える
- ブレインが作業を分解し、worktree ごとに実行役を起こす
- 実行役が手を止めたら（`TeammateIdle`）、ブレインが結果を見て次を指示する
- どのセッションが何を触っているかが一覧で見える
- 承認待ちのセッションが埋もれない（並列で一番壊れるのがここ）
- 終わったセッションは worktree ごと畳める

**「コンテキスト共有」ではない。** ブレインと実行役は別セッションなので
コンテキストウィンドウは共有しない。共有されるのはメッセージと
ファイルシステム（worktree・`CLAUDE.md`・書き出した中間成果物）だけである。

これは欠陥ではなく利点で、実行役が窓を使い切ってもブレインの文脈は汚れない。
代わりに「**何を書き出して共有するか**」が設計の要点になる。
共有フォルダ `~/.izuna/teams/<team>/` を一つ決め、`--add-dir` で全員に渡す。
brief / tasks / summaries / decisions / log を置き、decisions と log は追記のみ。
**圧縮を跨いで残るのはここだけ**なので、口頭で伝えたことは残らないと考える
（詳細は CLAUDE.md §12）。

### 2. self-hosted forge（Forgejo）

**Izuna が Forgejo の API を直接叩く。** `gh` のような外部コマンドに頼らない。

- リポジトリの一覧と clone
- セッションの成果から Pull Request を作る
- PR / Issue の閲覧と、そこからセッションを起こす
- Forgejo Actions の実行状況を見る

Forgejo を選ぶ理由: 単一バイナリで 512MB で動き、PR・Issue・Wiki・
パッケージレジストリ・LFS・GitHub Actions 互換 CI が全部入る。
自宅サーバや VPS に置ける。

### 3. ターミナル（libghostty）

**当初の企画趣旨をここで果たす。** `ghostty-web` は libghostty-vt の
公式 WASM ビルドで、xterm.js 互換 API と Canvas レンダラを持つ。
Electron でも本物の Ghostty の VT 実装が使える。

- ツール出力を忠実な ANSI で描く
- worktree ごとのシェルにいつでも降りられる
- 必要なら対話版 `claude` をそのまま走らせる

## 完成の定義（v1）

**次の一連の流れが、Izuna から出ずに完結すること。**

1. Forgejo のリポジトリ一覧から一つ選び、clone する
2. Issue を選んで**ブレインのセッション**を起こす
3. ブレインが作業を分解し、**worktree ごとに実行役を起こす**（2 つ以上）
4. 実行役が手を止めたら、ブレインが結果を見て**次の指示を返す**
5. 承認を求められたら、**人間が**差分を見て許可/拒否する
6. Forgejo に push し、**PR を作る**
7. worktree を畳む

この 7 手が動けば v1 である。動かないうちは v1 ではない。

**5 は人間のまま残す。** ブレインに承認まで任せると、
並列で一番壊れる箇所を無人にすることになる。

### 測り方

- `pnpm verify` が緑
- 上の 7 手を人が実際に通せる（スクリーンショットを残す）
- 実行役 2 つを同時に走らせて、互いの worktree を壊さない
- **ブレイン → 実行役のメッセージが保留されずに届く**
  （権限モードのクラス不一致という既知の罠を踏んでいない。CLAUDE.md §12）

## やらないこと

意識して外す。あとで欲しくなっても、v1 では作らない。

- **Windows / Linux 対応**（macOS だけ）
- **モバイル / 同期 / 共同編集**（Nimbalyst の領域）
- **GitHub / GitLab 対応**（Forgejo に絞る。抽象化は 2 つ目の forge が要るまでやらない）
- **Claude Code 以外のエージェント**（Codex / Cursor / Copilot）
- **ブレインに承認を任せること**（承認は人間が持つ。§完成の定義 5）
- **3 階層以上のエージェント**（ブレインと実行役の 2 階層まで）
- **WYSIWYG エディタ・kanban・マインドマップ**（Nimbalyst の領域）
- **拡張機構・プラグイン SDK**
- **配布・自動更新**（自分の手元で動けばよい）

## 段階

| 段 | 内容 | 完了条件 |
| --- | --- | --- |
| 0 | セッション層 | ✅ 済（Agent SDK・権限承認の握手） |
| 1 | 会話 UI | 1 セッションを画面から動かせる。承認と差分が見える |
| 2 | `/` パレット | `supportedCommands()` の一覧を補完から実行できる |
| 3 | worktree 並列 | 人が起こした 2 セッションが同時に走る。一覧で状態が見える |
| 4 | ブレインと実行役 | ブレインが実行役を起こし、idle を受けて指示を返す |
| 5 | Forgejo | リポジトリ一覧・clone・PR 作成 |
| 6 | ターミナル | ghostty-web で worktree のシェルに降りられる |

段を飛ばさない。**1 が動く前に 4 を作らない。**
段 4 は魅力的だが、1 セッションを画面から動かせないうちに手を出すと、
何が壊れているのかが分からなくなる。

刺さらないなら「やらないこと」に足す。柱を増やすときは、
なぜ増やすのかをここに書いてから作る。
