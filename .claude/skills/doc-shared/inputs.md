# 入力の集め方と、集まらないときの畳み方

資料の skill 4 本（`doc-*`）が共有する。**入力が集まらなければ資料を作らない。**
空の表を出すことは、何も出さないことより悪い —— 読んだ人が「無い」と「読めなかった」を区別できない。

## 集めるもの

| 何 | どう取るか | 無いとき |
| --- | --- | --- |
| 目標・やらないこと | `docs/GOAL.md`。無ければ `README.md` | 人に「この期間の目標を 1 行で」と聞く。**自分で決めない** |
| open な Issue | `gh issue list --state open --limit 100 --json number,title,labels,body` | 下の表で分岐する |
| 直近の変更 | `git log --oneline -30` | git のリポジトリでなければ、その旨を資料に書く |
| 前の版 | `docs/plans/<資料名>/` の最新のファイル | 「最初の版」と書く |
| 今日の日付 | `date +%F` | —— |

## `gh` が返すもの（2026-09-11 に測った）

`gh` は状況によって**止まる場合と、空で成功する場合**がある。後者が危ない。

| 状況 | `gh issue list` の答え | どうするか |
| --- | --- | --- |
| GitHub の remote が無い | `no git remotes found` を出して失敗する | 人に「Issue の一覧を貼ってください（番号と題名）」と頼む |
| remote はあるが Issue が 0 件 | **`[]` を返して成功する** | **資料を作らない。**「open な Issue が 0 件なので作りません」と言って止まる |
| `gh` にログインしていない | 認証を促して失敗する | 人に貼ってもらうか、`gh auth login` を促す |

**`[]` が一番危ない。** 成功して空が返るので、そのまま進むと空の表か、作り話の Issue が出る。
必ず件数を見て、0 なら止まる。

測り方（別の環境で確かめ直すとき）:

```bash
gh issue list --state open --limit 5 --json number                      # いまのリポジトリ
gh issue list --state open --limit 5 --json number --repo <o>/<空のリポジトリ>
```

## 貼ってもらうときの頼み方

```
Issue の一覧を貼ってください。1 行 1 件で「#番号 題名」の形で結構です。
本文が要るものがあれば、そのときに聞きます。
```

**推測で埋めない。** 貼られなければ資料を作らず、何が無かったかを言って止まる。
