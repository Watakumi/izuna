# 判定の記録（資料の skill 4 本）

`.claude/skills/doc-*` を書くときに集めた記述を、**一般ルール / 範囲つきの例 / 不採用**に仕分けた記録。
2026-09-11 に判定した。資料が更新されたら再判定する。

判定の条件は 3 つ。裏づけがあるか、同じ条件で矛盾する記述がないか、単一の環境に限らないと言える根拠があるか。

## 一般ルール（3 つとも満たす。本体に通常の指示として書く）

| 記述 | 裏づけ |
| --- | --- |
| 入力が空なら資料を作らず、何が無かったかを言って止まる | `gh issue list` は Issue 0 件で `[]` を返して成功する（測定。`inputs.md`）。止めなければ空の表か作り話が出る |
| 推測で埋めず「決めてほしいこと」に残す | 資料は事実の形をしているので、推測が混ざると見分けられなくなる（`writing.md`） |
| 上書きせず日付つきの版を足し、前の版からの変更を書く | 利用者の指示（2026-09-11）。資料ごとの歴史を `git log -- docs/plans/<資料名>/` で追うため |
| 根拠を 1 行添える（Issue 番号・commit・GOAL の節） | 根拠が無いと、読んだ人が確かめられない |
| 成功を実行後に観測できる条件で書く | 「作った」は成功の証拠にならない |
| 日付は `date +%F` で取る | 推測で書くと版の順序が壊れ、しかも止まらない |

## 範囲つきの例（裏づけと矛盾なしは満たすが、環境非依存の根拠が無い）

**この環境のこの設定で確かめた例**として読むこと。別の環境では確かめ直す。

| 記述 | 確かめた範囲 |
| --- | --- |
| `gh issue list --state open --limit 100 --json number,title,labels,body` が通る | Izuna のリポジトリ、`gh` ログイン済み、2026-09-11 |
| Issue 0 件で `[]` が返る | `Watakumi/homebrew-izuna`、2026-09-11 |
| remote が無いと `no git remotes found` で失敗する | 一時ディレクトリの空リポジトリ、2026-09-11 |
| エージェントは今日の日付を知っている | Izuna が起こす haiku のセッション（`systemPrompt` は `claude_code` の preset）、2026-09-11 に「2026-09-11」と答えた。**それでも `date +%F` で確かめる** —— 間違えても止まらない箇所なので、安い保険を掛ける |
| `docs/plans/` は版管理に入る | Izuna のリポジトリ、`git check-ignore` が何も出さない、2026-09-11 |
| Example Mapping の規則は 3〜7 個が目安 | Example Mapping の通説。Izuna では測っていない。超えたら分割を**提案する**にとどめる |

## 不採用（裏づけが弱い、または矛盾が解けない。書かない）

| 書かなかった記述 | 理由 |
| --- | --- |
| 「Now は次の 1〜2 週間で終わるもの」 | 期間の根拠が無い。最初の版に書いてしまったので、観測できる条件（着手済み・依存が解けている）に書き直した |
| 「Issue が 100 件を超えたら上位 20 件に絞る」 | 上限の根拠が無い。測っていない |
| skill から Forgejo の Issue を読む | ボットのトークンはエージェントの手に渡らない（security.md §26）。口を作るかは未決（Issue #52） |
| 「資料は PR にして PdM にレビューさせる」 | Izuna の二段の流れには乗るが、PdM がいる前提を置けない。手順としては書かず、置き場だけ示す |

## 再判定するとき

- `gh` の挙動が変わった（`inputs.md` の表を測り直す）
- Forgejo の Issue を読む口ができた（Issue #52）
- 範囲つきの例を別の環境で追試して裏づけが増えた → 一般ルールに上げる
