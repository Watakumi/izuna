# Now / Next / Later

open な Issue を 3 列に振り、**順番を話す土台**を作る。期日は切らない。
決まらなかったものは「決めてほしいこと」に残す —— この資料の値打ちは、
並んだ順番より**決まっていないことが名指しで出てくること**にある。

## いつ使い、いつ使わないか

使う:

- 次に何をするか、人と話す前に整理したい
- Issue が溜まって、どれが先か分からなくなった
- 前に作った版から何が動いたかを見たい

使わない:

- **open な Issue が 0 件のとき。** 並べるものが無い。作らずに止める
- 1 つの Issue を掘り下げたいとき → `doc-example-map`
- なぜ作るかから問い直したいとき → `doc-impact-map`
- 出来上がった姿を先に書きたいとき → `doc-working-backwards`

## 手順の形式

順序つきの手順。**1 → 4 を飛ばさない。** 入力が集まらなければ 2 で止まる。

## 手順

### 1. 入力を集める

`../doc-shared/inputs.md` の表のとおりに集める。要るのは 4 つ。

- `docs/GOAL.md`（無ければ `README.md`）の目標と「やらないこと」
- `gh issue list --state open --limit 100 --json number,title,labels,body`
- `git log --oneline -30`
- `docs/plans/now-next-later/` の前の版（あれば）と `date +%F`

### 2. 入力が足りるかを見る（**止まる判断**）

| 見るもの | 足りない | どうするか |
| --- | --- | --- |
| Issue の件数 | **0 件** | 資料を作らない。「open な Issue が 0 件なので作りません」と言って終わる |
| `gh` の結果 | 失敗した | 人に一覧を貼ってもらう。貼られなければ作らない |
| 目標 | GOAL も README も無い | 人に「この期間の目標を 1 行で」と聞く。**自分で決めない** |

`gh` は Issue 0 件でも `[]` を返して**成功する**。件数を見ないと、空の表か作り話が出る。

### 3. 並べる

Issue を 1 件 1 枚として、次の条件で振る。**条件は観測できるものだけを使う。**

| 列 | 入れる条件（観測できるもの） |
| --- | --- |
| **Now** | 枝がある、直近 30 commit が同じ領域を触っている、または依存が全部解けていて費用が見積もられている |
| **Next** | Now のどれかに依存する、または Now が終われば条件が揃う |
| **Later** | 上のどちらでもない。**順番が決まらない理由を書く** |

- 根拠を 1 行添える（Issue の番号・commit の短縮ハッシュ・GOAL の節）
- GOAL の「やらないこと」に当たるものは、Later にも置かず**「置かない」の節に列挙する**
- 1 つの Issue は 1 列にだけ置く。迷ったら Later に置き、理由に「順番を決める材料が無い」と書く
- 判断が人に要るものは、列に置いたうえで「決めてほしいこと」にも書く

### 4. 書く

`../doc-shared/versioning.md` のとおりに版を足す。置き場は `docs/plans/now-next-later/`。

```markdown
# Now / Next / Later（YYYY-MM-DD）

前の版（YYYY-MM-DD）からの変更: ...    ← 最初なら「最初の版」

| Now | Next | Later |
| --- | --- | --- |
| **#12** 題名 — 根拠 | **#7** 題名 — 根拠 | **#3** 題名 — 根拠 |

## 置かない
- #5 題名 — GOAL の「やらないこと」の X に当たる

## 決めてほしいこと
1. **#n #m** 問い — 決めるのに要る材料。費用が分かるなら添える
```

## 適用範囲

- **出どころ**: Now / Next / Later は Janna Bastow らが広めたロードマップの形。期日を切らないのが要点
- **対象**: Issue が付いている git のリポジトリ。Izuna では `docs/plans/` が版管理に入ることを確かめた（2026-09-11）
- **当てはまらなくなる条件**:
  - Issue を使っていないリポジトリ（貼ってもらうしかない。手順としては通る）
  - 期日が契約で決まっている仕事（この資料は期日を扱わない。別の形が要る）
  - Issue が数百件ある場合（絞り方を測っていない。`../doc-shared/judgement.md` の不採用を見ること）
- **確かめた環境**: Izuna のリポジトリ、`gh` ログイン済み、2026-09-11

## 実行後に確かめる

**「作った」を成功にしない。** 次を全部満たすこと。

```bash
ls docs/plans/now-next-later/              # 新しい版があり、前の版も残っている
git log --oneline -1 -- docs/plans/now-next-later/
```

- 入力にあった Issue が、3 列と「置かない」を合わせて**ちょうど 1 度ずつ**出る（数が合う）
- 根拠の無い行が 0 行
- 「決めてほしいこと」の件数が、本文で未決としたものの数と一致する
- 表が 20 行を超えていない（超えたら畳む。`../doc-shared/writing.md`）

## 受け取る側が得るもの

- `docs/plans/now-next-later/YYYY-MM-DD.md`（版）と `README.md`（索引）
- そのまま人に見せて、順番と「決めてほしいこと」を話せる状態
- 報告は**パスと「決めてほしいこと」の件数だけ**を 1 行で。資料の中身を会話に繰り返さない
