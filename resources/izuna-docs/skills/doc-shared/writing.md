# 資料に書いてはいけないこと

資料の skill 4 本（`doc-*`）が共有する。どれも一見もっともらしく、読み返しても気づきにくい。

| 書いてはいけない | なぜ | 代わりにどう書くか |
| --- | --- | --- |
| 根拠の無い順番（「次にこれ」とだけ書く） | 読んだ人が確かめられない。議論が「なぜそれが先か」から始まる | Issue の番号・commit・GOAL の節を 1 行添える。無ければ「順番を決める材料が無い」と書く |
| 期間の見積もり（「2 週間で終わる」） | 測っていない。外れても誰も気づかない | 観測できる条件で書く（「着手済み」「依存が解けている」）。費用を書くなら「半日」など、根拠のある単位で |
| 分からないことを埋める | 資料が事実の形をしているので、推測と事実が見分けられなくなる | 「決めてほしいこと」「疑問」「未定」の節に、決める人と要る材料つきで残す |
| 利用者の声を作って書く | 作り話が引用として一人歩きする | 書くなら「想定。作り話である」と明記する |
| 出典の無い数値 | 検算できない | 出どころ（Issue、commit、測定した日）を添える。無ければ書かない |
| その場の判断を一般の規則として書く | 別の状況に持ち込まれて壊れる | 「この環境で確かめた例」と範囲を明記する |
| 実行できない手順（未定義の道具や値を含む） | 動かないまま採用され、原因が分からなくなる | 実行できる形にするか、案だと明記して文章で書く |

## 成功の定義

「資料を作った」「エラーが出なかった」を成功にしない。**実行後に観測できる条件**で書く。

- ファイルが存在する（`ls` で見える）
- 入力にあった Issue が、資料のどこかに 1 度だけ出る（数が合う）
- 「決めてほしいこと」の件数が、本文と一致する
- 前の版が残っている

## 長さ

資料は読まれなければ意味がない。**1 画面で全体が見えることを優先する。**
表が 20 行を超えたら、優先度の低いものを別の節に畳むか、資料を分ける。
